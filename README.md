# P2PStream

Плагин P2P-стриминга для **Vesktop** (через [veskforge](https://github.com/Microck/veskforge) или наш **VencForge**) — замена Discord Go Live без лимитов Discord.

> Устройство плагина, разбор всех проблем/ограничений и диагностика — в [PROJECT.md](PROJECT.md).

- до **100 Мбит/с** видео (Discord даёт ~8), разрешение до 4K, до **240 FPS**
- задержка **30–80 мс** в mesh-сети до 5 зрителей (WebRTC P2P, без сервера)
- кодеки: **AV1 / VP9 / H.264** (автовыбор), стерео-звук Opus до 512 кбит/с
- **умный звук приложения** (v1.4, Windows 10 2004+): стримишь окно — в эфире только звук этого приложения; стримишь весь экран — вся система **без Discord**. Тот же механизм WASAPI Process Loopback, что использует сам Discord; недоступен — автоматический откат на системный звук
- **нативный пикер трансляции** в стиле Discord: сетка источников с превью, живой предпросмотр, качество (как «Stream Mode»), звук — и выбор «P2P» или «Обычный стрим Discord»
- **плитка стрима в звонке как у обычного Go Live**: LIVE, метка **P2P**, качество (например 1080p60), живое превью, кнопка «Смотреть» открывает P2P-просмотр
- окно просмотра: зум к курсору, **PiP**, мини-плеер (сворачивается, не рвёт эфир), фуллскрин, статистика (битрейт/FPS/задержка)
- **тихий сигналинг (v1.10)**: служебные коды едут сообщениями `@silent` (штатный флаг Discord «без уведомлений») — адресные (join/SDP/ICE) в **ЛС между стримером и зрителем**, анонсы в голосовой канал; каждое сообщение удаляется за ~2 с. НИ У КОГО никаких уведомлений, никто кодов не видит; SDP/ICE зашифрованы ECDH + AES-GCM даже внутри ЛС. Альтернатива — свой MQTT-брокер (Cloudflare Worker из коробки или mosquitto на своём сервере), тогда Discord вообще не участвует в сигналинге
- команды `/p2p-start`, `/p2p-stop`, `/p2p-watch`, **`/p2p-doctor`** (диагностика в консоль для тестов — v1.5)

## Установка (veskforge)

1. Установи [veskforge](https://github.com/Microck/veskforge) (нужны Git и Node.js LTS).
2. В veskforge добавь плагин источником **Git**:
   ```
   https://github.com/shxtai/P2PStream
   ```
   (veskforge принимает только HTTPS-ссылки на корень репозитория; именно Git-источник даёт плагину native-часть — сетку источников и умный звук)
3. Нажми **Build** — veskforge сама клонирует Vencord, вставит плагин в `src/userplugins` и соберёт dist.
4. Нажми **Apply / Launch** — Vesktop переключится на эту сборку.
5. В настройках Vencord: **Plugins → P2PStream → Enable**.

Плагин нужно поставить **обоим**: и стримеру, и зрителям.

## Установка (VencForge — свой билдер)

**[VencForge](https://github.com/shxtai/VencForge)** — наш собственный менеджер сборок с графическим интерфейсом: умеет то же, что veskforge, плюс работает с **обычным Discord** (не только Vesktop), принимает плагины **Git-ссылкой, папкой или файлом** (как veskforge), сам обновляет Vencord и плагины из Git, сам перепатчивает Discord после его обновлений и умеет автообновление по расписанию.

1. Скачай **VencForge-Setup.exe** (или Portable-версию) со страницы репозитория и запусти.
2. Нажми **«Обновить и установить всё»** — приложение само:
   - проверит зависимости и при необходимости скачает портативный Node.js (без прав администратора),
   - склонирует в `%APPDATA%\VencForge\workspace` свежий Vencord и плагины из списка (по умолчанию P2PStream с GitHub),
   - соберёт Vencord с плагинами, положит сборку в `%APPDATA%\VencForge\dist`,
   - пропатчит все установленные Discord (Stable/PTB/Canary; оригинал сохраняется как `_app.asar`) и подключит **Vesktop**, если он стоит — работает и на «голый» Discord, и на уже стоящий Vencord от официального инсталлера,
   - выключит автообновление Vencord (чтобы официальный апдейтер не затирал нашу сборку).
3. Дальше VencForge = обновление всего в один клик: Vencord, плагинов, перепатчивание после апдейтов Discord.

Добавить другие плагины: вкладка **«Плагины»** → Git-ссылка / папка / файл → **«Собрать Vencord»**.

### Обновление

Просто нажми **Build** в veskforge ещё раз — она сама делает `git fetch` из репозитория и пересобирает плагин последней версии. Обновления Vencord плагин не ломают: veskforge пересоздаёт `src/userplugins` из своего манифеста при каждой сборке.

### Установка без репозитория (локально)

- **Папкой**: скачай папку с файлами плагина и добавь её в veskforge источником *Local folder* (внутри должен быть `index.tsx`).
- **Одним файлом**: возьми `P2PStream.tsx` из релизов и добавь как *Local file* (файл обязан оканчиваться на `.ts`, `.tsx`, `.js` или `.jsx`).

## Как стримить

1. Подключись к голосовому каналу и нажми кнопку **«Демонстрация экрана»** — откроется пикер P2PStream (окно выбора стрима Discord подменяется целиком):
   - сверху — **сетка источников** (экраны и окна с превью) — клик выбирает источник и сразу запускает живой предпросмотр;
   - **Качество** — разрешение (480p–4K/родное) и FPS (15–240) рядами, как в новых сборках Discord;
   - **Режим** — «Игры» (плавное движение) / «Кино» (чёткая картинка) — это настоящий `contentHint`, тот же, что использует Discord;
   - переключатель **звука**, «Дополнительные настройки» — кодек и битрейт;
   - зелёная кнопка — **Начать P2P-трансляцию**, рядом — **«Обычный стрим Discord»** (дефолтный Go Live; если источник уже выбран, лишний пикер не показывается).
2. Зрители видят твой эфир **прямо в звонке** как обычный стрим (плитка с LIVE и меткой P2P). Превью на плитке живое: у зрителей кадры приходят по P2P-каналу ещё **до** подключения к просмотру. Клик по плитке открывает просмотр; пилюли внизу экрана и `/p2p-watch` тоже работают.

> До 240 FPS стабильнее всего при захвате **всего экрана**: окна обновляются только при перерисовке, так что статичное окно может выдавать меньше кадров.

### Про звук

- **По умолчанию — «умный» режим (v1.4)**: стримишь **окно/приложение** — в эфире только звук этого приложения; стримишь **весь экран** — звук всей системы, **кроме Discord**.
- Как это работает: встроенный в плагин хелпер (`native/p2paudio.c`, ~38 КБ) использует **WASAPI Process Loopback** — ровно тот же нативный механизм, которым Discord захватывает звук приложения. Хелпер распаковывается в `%APPDATA%\vesktop\p2pstream\` и запускается только на время эфира; PCM едет в рендерер и подмешивается в WebRTC-поток как обычная аудиодорожка.
- Требования: **Windows 10 2004 (build 19041)+**, Vesktop/Vencord-сборка с main-частью плагина (папка или репозиторий; **однофайловый** вариант без нативного звука — сразу системный звук). Звук UWP-приложений из Магазина может не захватываться (их процессы живут вне окна — ограничение Windows).
- Если умный режим недоступен (старая Windows, другой клиент), плагин автоматически работает по-старому: системный loopback целиком; в настройках можно выбрать «Системный звук всегда» или «Без звука».

### Профили Игры / Кино

- **Игры** — 1080p60, битрейт 30 Мбит/с, буфер 0 мс, оптимизация движения (минимальная задержка);
- **Кино** — 1080p60, битрейт 20 Мбит/с, буфер 150 мс, оптимизация детализации.

Профиль переключается на живом эфире: кнопками в панели внизу экрана или в пикере — FPS/разрешение/битрейт/контент применяются **на лету**, без перезапуска стрима.

## Сигналинг без уведомлений и без чата (v1.10)

Соединить двух плагинов надо как-то без видимых сообщений. Порядок попыток:

1. **MQTT-брокер** (если включён в настройках) — Discord не участвует вовсе.
2. **Тихий Discord-транспорт** (по умолчанию) — штатные сообщения с флагом `SUPPRESS_NOTIFICATIONS` (тот же, что у «@silent» в клиенте):
   - адресные сигналы (join, offer/answer, ICE) — в **ЛС между стримером и зрителем**: посторонние их не видят никогда;
   - broadcast (анонсы «я в эфире», discovery) — в голосовой канал;
   - всё самоудаляется через ~2 с (реальный id приходит в ответе REST);
   - **уведомлений нет ни у кого** — ни пушей, ни значков, ни упоминаний;
   - SDP/ICE запечатаны ECDH P-256 + AES-GCM — даже Discord не видит IP-адреса внутри сигналов.
3. Видимые коды с автоудалением — последний фолбэк, если REST-отправка не удалась.

Секретность: ключ шифрования выводится из пары одноразовых ECDH-ключей, которые обменяются в join/offer. Активный MITM невозможен без подмены ключей «на лету» — а это уже уровень Discord-инфраструктуры, а не случайных читателей канала.

### Свой брокер (сигналинг полностью мимо Discord)

Если хочешь, чтобы служебные сообщения не появлялись даже на 2 секунды:

- **Cloudflare Worker (2 минуты, бесплатно, без своего сервера)**: возьми `cf-worker/worker.js` из репозитория — это мини-MQTT на Durable Objects. Деплой: dash.cloudflare.com → Workers → Create → вставить файл → добавить binding Durable Object (класс `Broker`, имя `BROKER`) → в настройках плагина: брокер включён, адрес `wss://<имя-worker>.<аккаунт>.workers.dev/mqtt` (у стримера и зрителя одинаково).
- **Нетбук/домашний сервер**: любой MQTT-брокер с WebSocket-_listener'ом, например mosquitto:
  ```
  # /etc/mosquitto/conf.d/p2ps.conf
  listener 8084
  protocol websockets
  allow_anonymous true
  ```
  Адрес в настройках: `wss://<хост-нетбука>:8084` (IP меняется — прикрути DDNS или сиди в одной сети). Хорошо сочетается с уже развёрнутым TeamSpeak.
- Публичные брокеры (emqx/hivemq/mosquitto) остались в списке по умолчанию, но у части провайдеров режутся DPI: WSS открывается, а CONNECT молча дропается. Если в `/p2p-doctor` брокер «не подключён (нет CONNACK)» — это он и есть; оставайся на тихом Discord-транспорте или ставь свой Worker.

## Если зритель не подключается (ICE failed) — ретранслятор Cloudflare

Признак: в консоли (F12) у обоих есть `← offer` / `← answer`, а затем `ICE [...]: checking → disconnected → failed`. Значит, сигналинг работает, но прямые пакеты между вашими сетями не проходят (NAT/фильтрация провайдера). Нужен ретранслятор — бесплатный TURN от Cloudflare (до 1000 ГБ в месяц). **Настраивает только стример**, зрителям учётки передаются автоматически внутри зашифрованного оффера.

1. Зарегистрируйтесь на [dash.cloudflare.com](https://dash.cloudflare.com) (бесплатно, карта не нужна).
2. В меню слева: **Realtime → TURN Server → Create** (название любое).
3. Скопируйте **Turn Token ID** и **API Token** (токен показывается один раз).
4. Vencord → Plugins → P2PStream: вставьте их в «Cloudflare TURN — Key ID» и «Cloudflare TURN — API token».
5. Проверка: `/p2p-doctor` → строка `TURN: Cloudflare: N сервер(а)`. Для теста можно включить «Отладка: соединяться только через TURN» — в консоли будет `соединено relay ↔ …`.

WebRTC сам выбирает путь: где прямой работает — идёт напрямую, иначе через Cloudflare (в том числе по TLS:443, если UDP режется). Через ретранслятор 30 Мбит/с ≈ 13 ГБ в час — при долгих эфирах снизьте битрейт.

## Настройки

- Режим кнопки «Демонстрация экрана»: свой пикер (P2P или обычный стрим) / буст Go Live / без изменений
- **Звук**: Умный (звук приложения / система без Discord) / системный всегда / без звука
- **Показывать P2P-эфир в звонке как обычный стрим** (плитка с превью) — можно выключить, если что-то не так
- Разрешение 720p–4K/родное; FPS 30–240; видеобитрейт до 100 Мбит/с; аудио до 512 кбит/с (стерео)
- Кодек: Авто (H.264 → VP9 → AV1) / ручной
- Буфер зрителя 0–500 мс (0 = минимальная задержка)
- STUN (по умолчанию Google + Cloudflare) и свой TURN — нужен, только если у ОБОИХ «плохой» (симметричный) NAT; свой тип NAT показывает `/p2p-doctor` (строка `NAT:`)
- Брокер сигналинга: выключен (тихий Discord-транспорт) / свой MQTT (WSS-адрес)

## Совместимость

Формат — стандартный Vencord userplugin (`index.tsx` + файлы рядом), поэтому плагин также ставится обычным путём: клон [Vencord](https://github.com/Vendicated/Vencord) → `src/userplugins/P2PStream` → `pnpm build` → `pnpm inject`.

## Версии

- **1.17.1 — битрейт не скачет 80 → 40**. Авто-качество больше не режет поток из-за малых потерь (< 5% без запросов ключевых кадров), которые WebRTC сам восстанавливает; резкое снижение — только при реально плохом канале (> 15% или шторм PLI с потерями), иначе мягко ×0.8; возврат после 6 с чистого канала +20% каждые 4 с (с 40 до 80 Мбит/с ~18 с вместо минуты).
- **1.17.0 — чёткая картинка в динамике, FPS не ниже 60**. Битрейт делится на все кадры: при 110 FPS в 1440p быстрые сцены «мылились». Теперь FPS выше 60 включается, только если на него хватает бит на кадр (~0.16 бит/пиксель/кадр, с запасом против дёрганья): например, 1440p при 50 Мбит/с — 60 FPS, 1080p при 50 Мбит/с — 120 FPS. Ниже 60 авто-качество FPS не опускает никогда: при нехватке процессора или канала в режиме «Игры» снижается разрешение, а не плавность.
- **1.16.1 — поток не толще канала**. Реальный лог: в настройках 100 Мбит/с, канал ~36, энкодер выдавал 63 Мбит/с — потери 15%, 1227 NACK, 18 заморозок у зрителя. Теперь итоговый битрейт = min(потолок по потерям, 90% оценки канала самого WebRTC, максимум из настроек); потери считаются по накопленным счётчикам (раньше мгновенный снимок часто показывал 0 при реальных 15%); запросы ключевых кадров при NACK не считаются сбоем декодера.
- **1.16.0 — звук без провалов и ровный FPS во время игры**. Нативный звук под нагрузкой игры пропадал: забор PCM раз в 40 мс опаздывал, ворклет при рывке подачи обрезал очередь (слышимый пропуск), а после опустошения играл крупицами. Теперь забор раз в 20 мс, буфер копит 80 мс перед стартом/после провала и обрезает только накопления > 350 мс; хелпер звука с повышенным приоритетом. Модель (5×60 с под «игровыми» задержками): провалов 159 → 19, выброшенного звука 6.5 с → 0. Видео: если энкодер упирается в процессор (VP9 + игра) и FPS скачет — авто-качество ставит ровные 48 или 30 FPS (плавнее «рваных» 35–60), а когда процессор свободен — возвращает.
- **1.15.0 — авто-смена кодека и честное авто-качество**. Реальный лог показал «статичный кадр» при чистом канале (потери 0%), но с непрерывными запросами ключевых кадров от зрителя: его декодер не принимал поток. Теперь хост распознаёт это (запросы ключевых кадров без потерь или зависший энкодер) и сам переключает ЭТОМУ зрителю кодек H.264 → VP9 → VP8 с пересогласованием на лету. Авто-качество больше не принимает такие запросы за перегрузку (раньше зря душило поток до 1.5 Мбит/с). `/p2p-doctor`: кадры захвата vs закодировано, кодек у зрителя.
- **1.14.0 — авто-качество под канал**. Поток больше не долбит фиксированным битрейтом в канал, который его не тянет: хост раз в 2 с смотрит отчёты зрителя (потери, запросы ключевых кадров, рост задержки) и снижает битрейт/разрешение именно этому зрителю (1440p → 1080p → 720p), а на чистом канале плавно возвращает. Случайные потери (туннель/фильтр) отличаются от перегрузки — картинка не душится зря. У зрителя буфер сам растёт при заморозках (до 300 мс) и уменьшается на стабильном канале. На панели хоста — «авто ↓ N Мбит/с», когда поток снижен. `/p2p-doctor` во время эфира показывает подробную статистику потока. Выключается настройкой «Авто-качество».
- **1.13.0 — ретранслятор Cloudflare TURN**. Реальный тест показал: сигналинг работает, но прямые UDP-пакеты между некоторыми сетями не проходят (ICE failed). Добавлен бесплатный TURN от Cloudflare: ключ задаёт только стример, зрителям учётки приходят в зашифрованном оффере; учётки запрашиваются из main-процесса (мимо CSP Discord). Отладочный режим «только через TURN». Фикс: остановка стрима кнопкой Discord больше не воспринимается как запуск; источник из нового формата Go Live (`settings.desktopSettings.sourceId`) распознаётся. Сквозной тест проверяет и путь через ретранслятор.
- **1.12.0 — надёжный сигналинг**. Сообщения Discord иногда теряются — раньше потеря одного оффера/ответа срывала подключение. Теперь адресные сигналы доставляются с подтверждением и повторами (как в TCP), повторы собираются из кусков разных попыток; проверено сквозным тестом при потере 50% сообщений. Зритель снова сообщает свой внешний адрес (раньше ответ уходил только с локальным `192.168.x.x` — между разными сетями соединение не собиралось). Убран мёртвый публичный TURN (openrelay отвечал ошибкой и только тормозил подключение на 15+ с). `/p2p-doctor` показывает тип NAT. **Обновиться нужно обоим.**
- **1.11.0 — подключение зрителей и умный звук наконец работают**. Зритель видел эфир, но не мог подключиться: ключ шифрования сигналов не экспортировался, а при первом оффере создавались две разные пары ключей. Оффер теперь сжимается до шифрования (~3 сообщения вместо ~11, без 429 и дублей в чате). - **1.10.0 — тихий сигналинг без уведомлений + фикс фуллскрина**. Служебные коды больше не видны никому и не дёргают уведомлениями: адресные (join/SDP/ICE/leave) уходят в **ЛС между стримером и зрителем**, broadcast (анонсы/discovery) — в голосовой канал, всё с флагом `@silent` (SUPPRESS_NOTIFICATIONS, отправка через REST — реальный id для самоудаления возвращается сразу) и автоудалением через ~2 с.
